# 支付可靠性加固与实测记录（2026-11-18）

本轮修改实际支付运行代码，不把前两轮的参考模块或脚本自测当作生产支付验收。未上线，未修改日常主库或线上配置，未将故障注入、夹具、模拟支付写入生产。

## 本轮改动

1. PaymentInboxRunner生产默认开启4条有界消费通道，可用qingfeng.payment.inbox.worker-concurrency配置1..32。每条通道同一时刻最多一个任务，另保留一个对账任务槽，反复调度不产生无限任务队列。跨渠道轮询索引改用原子轮转，避免并行后竞态和下标溢出。
2. PaymentInbox已持久化的任务如果连续因worker宕机丢失租约，最多执行8次，下一次领取时转MANUAL并保留审计，不再无限重领。合法渠道pending等待仍沿用原有预算归还及7天截止规则。
3. MANUAL审计提交后才输出payment_manual_review错误事件，事务回滚不会发出“已进入人工复核”的误报。不输出回调正文、密钥或原始异常消息。需为该事件配置日志告警及人工处理人；本轮没有向外部平台发送通知。
4. 修复Stripe回调被误分到普通写请求60次/分钟限流桶的问题，和PayPal一样使用独立支付回调桶。新增qingfeng.payment.webhook.rate-limit-per-minute配置，默认保留600次/分钟/渠道，支持明确的容量预算；不取消验签、过载保护或普通用户写限流。默认额度本身不能宣称支持持续100TPS；部署示例12000/分钟只表示入口预算，不能替代实测。使用Redis时为集群共享额度，本地桶为单实例额度。
5. 真实InnoDB测试改用16连接的有界Hikari池，避免旧测试每次查询新建TCP连接耗尽本机端口。同步修复旧邀请奖励断言20→19，并给完整应用测试明确设置数据库会话UTC。

## 测试口径

- 使用本机独立MySQL 8.0.46/InnoDB实例及全新测试schema，完整应用使用16连接池。
- Stripe/PayPal渠道权威查询由测试网关替身返回已登记的合成事实；真实HTTP、Stripe签名校验、数据库迁移、事务、账本、权益及付款身份绑定使用实际应用代码。
- 不等于Stripe/PayPal真实Sandbox验收，不等于渠道TPS或生产服务器容量。
- 同一订单50并发相同event ID，再加不同event ID及晚到失败/取消通知；100独立用户并发到账、并发扣减；同用户50并发争抢100积分，每次扣3，必须33次成功、17次余额不足、余1分。
- 核对订单、流水、余额和权益投影；测量HTTP P99、不同用户扣减P99及MySQL锁等待/死锁增量。
- 小样本突发数据不能代表持续压测结果或极限TPS，不用“全部返回200”替代最终到账断言。

## 高可用边界

应用任务可由多个实例竞争领取，实例暂停/租约过期/重启后仍通过数据库token和幂等保持可恢复。已存在的完整应用上下文重启与事务回滚用例仍须通过。

要声称生产高可用，仍必须具备并验证：至少两个独立应用/worker实例、流量切换与健康检查、具有明确RPO/RTO的MySQL复制与故障切换、旧主隔离、独立监控告警及渠道重投/主动对账。当前仓库中的单个systemd服务配置与进程自动重启不能证明这些条件成立。

本轮没有切换生产拓扑，没有强杀共享MySQL测试实例，也没有完成主从切换或生产节点失效演练。因此不能给出“生产高可用已保证”的结论。
