# KIE音乐结果解析兼容

2026-11-03，本地修复，未部署。

## 原因

本机出现任务长时间显示「谱曲与演唱」。只读检查发现：任务已经受理，前两次查询正常，之后连续出现 `QUERY_RETRY`。KIE 原任务实际返回 `state=success`，成品音频位于：

```text
data.resultJson（可能是JSON字符串或对象）
  └─ resultObject
       └─ lyricsData[]
            ├─ audio_url
            ├─ stream_audio_url
            ├─ id
            └─ duration
```

旧解析只检查根级 `sunoData/data/tracks/resultUrls`，找不到该成品地址，抛出异常并进入查询退避。因此页面仍保持RUNNING，不能据此判断供应商仍在谱曲。

## 修复

- 音频地址与音频元数据共用结果分组读取，兼容 `resultObject.lyricsData`，同时保留旧格式。
- `resultJson` 同时支持字符串和直接对象；成品地址、音频ID和时长按同一条记录绑定，旧曲源信息查找仍匹配对应版本。
- 不将 `stream_audio_url` 当作完整音频，不因解析失败重复生成歌曲。
- 任务有 `QUERY_RETRY` 时，弹窗明确提示正在核对结果、尚未确认最新状态，不继续只显示正常谱曲提示。

## 本地验收

37项后端针对性回归通过，覆盖供应商解析、持久化执行与局部编辑；57项前端测试、类型检查和构建通过。新增测试包含嵌套结果的字符串/对象形式、版本元数据匹配及仅有流式地址时拒绝完成。

受影响的这条本地任务已用修复后的只读查询及原归档链路恢复：`RUNNING → SAVING → SUCCEEDED`。保存约3.6MB音频并确认可读取。恢复限定单个已受理任务，沿用供应商锁及任务租约，没有新提交音乐生成请求。

IDEA中已经加载的旧Java类不会因源码修改自动生效。重启本地后端后，后续任务才会使用新解析。当前用户的8080/5173进程未被停止，生产未部署。

## 歌词时间轴的同源问题

后续检查发现，歌词时间轴模块也单独维护了旧版音频编号解析。因此歌曲归档恢复后，时间轴仍无法从 `resultObject.lyricsData` 找到对应版本，返回FAILED。初次检查时该本地记录已有6次失败尝试，不能据此认定供应商实际执行了6次时间轴请求。

现已抽出 `KieAudioResults`，歌曲归档、源版本查询与时间轴共用结果分组和音频身份匹配。过期签名允许变化，业务查询参数仍须一致，防止同一路径的不同音频版本误配。

新增嵌套结果（对象/字符串）时间轴测试，以及不同版本查询参数不匹配时禁止POST的测试；相关49项后端回归全部通过。统一接口与兼容接口仍由配置选择，不自动回退，不自动重复POST。

获得用户单独授权后，已为这条本地歌曲调用1次真实兼容时间轴接口，HTTP200/业务码200，结果READY，保存26行时间轴。调用次数受一次性客户端限制，没有重新生成歌曲。刷新现有作品页即可读取缓存；后续歌曲仍需IDEA后端重启后使用修复。生产未部署。

接口依据：[KIE Get Timestamped Lyrics](https://docs.kie.ai/old-model/suno-api/get-timestamped-lyrics)，以任务与音频版本共同定位时间轴。
