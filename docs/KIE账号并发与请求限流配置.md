# KIE账号并发与请求限流配置

日期：2026-11-08。状态：本地代码与公开默认配置；本轮未部署、未修改线上配置、未重启业务服务。

## 供应商限制与本站设置

用户提供的KIE账号账单截图明确写明：每个账号每10秒最多20个新生成请求，超额返回429且不进入队列；约100+并发任务是说明值，不是已经确认的硬并发上限。

据此设置：

| 项目 | 本站配置 | 说明 |
| --- | --- | --- |
| 活跃音乐任务准入 | 100首 | 包括排队、提交、生成、归档、待核对任务；第101个活跃请求暂不受理 |
| 单用户活跃音乐任务 | 1首 | 保留原保护，防止单用户占满资源 |
| 单供应商音乐在途分发 | 100首 | 本站预算，不代表已通过真实供应商或服务器100首压力验收 |
| KIE新建请求 | 最多18次/10秒，平滑发送 | 相邻获准发送间隔至少556ms，较20次硬限制留余量 |
| KIE只读请求 | 最多8次/秒，平滑发送 | 相邻许可间隔至少126ms，为查询上限留余量 |
| 音乐提交线程 | 2个/进程 | 等待速率许可时不持有数据库事务 |
| 音乐查询线程 | 4个/进程 | 独立于提交与归档 |
| 音频归档线程 | 2个/进程 | 控制内存、下载和OSS上传资源 |
| 执行循环间隔 | 500ms | 每个循环完成后等待，不是每个任务的供应商轮询周期 |

10位不同用户可以同时提交并进入处理，不再因为原全局3首限制而被拒绝。请求按账号速率陆续发送，无需等前一首完整生成后才提交后一首。实际完成时间取决于供应商、网络和归档，不作固定时延承诺。

## 配置位置

公开默认值：`Qingfeng_AI_Music/config/usage-limits.properties`。

```properties
qingfeng.usage.music.concurrent-per-creator=1
qingfeng.usage.music.concurrent-global=100
qingfeng.generation.max-in-flight=100
qingfeng.generation.submit-workers=2
qingfeng.generation.query-workers=4
qingfeng.generation.archive-workers=2
qingfeng.generation.scan-ms=500

qingfeng.providers.kie.rate-limit.scope=primary
qingfeng.providers.kie.rate-limit.creates-per-ten-seconds=18
qingfeng.providers.kie.rate-limit.reads-per-second=8
qingfeng.providers.kie.rate-limit.max-wait-seconds=30
```

每日次数与积分价格未在本轮调整。准入和分发仍是两个独立限制；本轮没有加入超出100首的自动等候队列或排队名次展示。

## 共享限流的实现边界

- 音乐生成、局部重唱、AI封面新建、歌词时间轴POST共用CREATE预算。
- 音乐、封面和歌词时间轴GET查询共用READ预算。
- 图片文件上传不计作模型新建请求；图片模型创建在上传之后、实际POST之前获取许可。
- 使用MySQL中的账号范围标识协调，默认`primary`；同账号的不同API Key仍保守共用一个范围，不将密钥或用户内容存入限流记录。
- 复用现有`generation_worker_lock`表，行名以`kie-rate:`开头，与音乐任务领取行分开；不新增迁移。
- 每次只尝试获取“现在可以发送”的许可，没有预订未来时段。未获得许可的检查不会向后推迟别人已经等待的时段。
- 时间来源为数据库；事务外等待，兼容多个Worker或应用进程共享主库。
- 默认最多等待30秒；音乐请求若在本地限流或数据库阶段失败，明确标记为未发送，退回积分并释放每日占额；不伪装为供应商已受理。
- 新建请求、查询和媒体归档仍不进行盲目付费重试。

该保护只能协调使用同一主库、相同scope的本站进程。供应商最终限制、同账号其他工具的调用、账户余额和网络异常仍可能导致429或其他失败，原错误分类和熔断继续生效。

KIE官方查询文档给出的Market任务查询上限是每API Key每秒10次；本站使用8次并将相关查询保守合并。参考：[任务详情与查询限制](https://docs.kie.ai/cn/market/common/get-task-detail)。

## 验证范围

- 10位用户通过真实业务准入并进入RUNNING，个人第2个活跃任务仍被限制。
- 100个活跃任务有明确准入边界，第101个被拒绝且不提交模型。
- 多个限流器实例在同一账号范围竞争时，不会重复消费同一时段许可。
- 创建与查询预算独立；拒绝检查不会预占未来许可；超时和中断不发请求。
- 音乐、封面、歌词时间轴适配器均接入对应预算，调用顺序通过离线HTTP验证。
- 限流失败的音乐任务退回积分和每日占额，重复处理不重复退款。
- 对共享限流和原任务并发使用独立MySQL专项验证；临时实例使用57286端口与固定测试库，不连接生产主库。

所有供应商均使用离线替身，未消耗真实KIE积分。这些验证不等于真实100首音乐同时生成的容量或听感验收。

本轮结果：后端完整`mvn verify`常规333项通过，27项临时MySQL专项在正常检查中按设计跳过、已另行全部通过；前端227项测试通过，类型检查与构建通过。真实MySQL临时实例已正常关闭。

## 发布与收紧

本轮增加了限流实现，首次生效必须发布匹配的新JAR，并同步线上`/etc/qingfeng-music/usage-limits.properties`；仅替换JAR可能仍被服务器旧的3首配置覆盖。发布前备份配置，按照`AGENTS.md`执行既定流程。

若需收紧：同时调整`concurrent-global`与`max-in-flight`，保留账号速率保护；将`max-in-flight=0`仅暂停新分发，继续查询与归档已有任务。配置调整需重启对应进程，不自动取消既有供应商任务。
