# 手机试听与重播优化

日期：2026-11-04。本轮执行本地修改、验证与构建，没有执行部署操作。收尾只读核对发现，线上公开播放器及相关页面资源已与本轮本地构建一致，见文末；这不代替真实手机验收。

## 为什么手机会等

旧的 `CompleteAudioCache` 对生成和导入歌曲使用 `fetch` 读取完整响应，全部下载成功后才创建 Blob 地址并调用 `play()`。页面里的“Preparing the full song / 下载完成后播放”就是这个客户端预下载进度，不是再次生成歌曲，也不是必须把文件保存到手机。

弱网会放大这段等待；等待网络结束后才调用 `play()`，也可能失去手机浏览器要求的直接点击上下文，出现还要再点一次的提示。仅凭截图不能确定用户那首《给妈妈的生日歌》的实际大小、手机实际吞吐或完整网络请求序列。

用户进一步确认是**同页听完后重播**。旧代码正常命中 Blob 时本应复用，但仍有以下需要处理的路径：关闭播放器会清空完整缓存；切换文件、页面重建或预加载替换可能再次读取；作品列表或版本列表设置过的队列会在结束后自动播放下一项，多个版本标题相同，容易看起来像同一首重新下载。没有用户设备的网络记录，不能把某一条静态路径直接认定为这一次手机现象的唯一触发条件。

## 本次修改

1. **取消整首下载门槛。** 用户点击后直接把已授权音频地址交给浏览器原生音频元素，通过现有 Range / 206 接口边加载边播放。调用 `play()` 前不等待整首 `fetch`。
2. **复用最近两首的原生媒体实例。** 暂停、自然结束后重播、同页关闭再打开及两版对比，不主动重设已存在的 `src`，不主动 `load()` 丢弃缓冲。超过两首按最近使用顺序释放，避免手机积累实例。
3. **区分收起与身份重置。** 普通关闭仅暂停并收起；找回码切换身份、当前分享读取失效时，`reset()` 清理全部原生实例与旧音频地址。
4. **结果页只播放当前歌曲，版本对比不自动换版。** 收藏列表的明确播放队列仍可连播，上一首 / 下一首功能保留。
5. **修改提示。** 去掉“整首下载进度 / 下载后播放”，改成“点击试听，边加载边播放”“正在连接音频”“正在播放”等实际状态；播放器错误仍保留重试入口。中英双语已同步。

音乐依然先由后端完整归档后才标记生成成功；本轮没有改为播放供应商临时流，也没有改生成、计费、文件归属或分享权限。下载按钮仍用于用户主动保存文件，不是试听前置步骤。

## 验证

- 前端 **70 项测试、14 个文件通过**，类型检查及生产构建通过。此前“整首缓存”的专用测试已替换成当前原生实例池、立即起播、重播、关闭重开、旧事件隔离、失效清理、版本连播、超时及片段试听测试；不能把不同实现的测试项数当作同一组测试直接比较。
- Chrome **18 项浏览器检查通过**，使用专用 `15173 / 18080`、隔离 H2 和用户提供的现有 MP3；未调用真实歌曲、歌词或图片模型。
- 测试文件 `3,971,598` 字节，约 181 秒。模拟下载速度 `64 KiB/s`、延迟 `100 ms`，**约 1.64 秒起播，起播时收到 92,197 字节，缓冲约 4.2 秒音频**。这是本机可控条件下的测量，不是公网手机的速度承诺。
- 随后恢复本机网络，以 16 倍速实际播放完整音频至 `ended`，再点击同页重播：仍使用同一实例、未重设 `src` 或调用 `load()`，音频请求总数仍为 1。首次测试中“未完整接收就跳到结尾”的情况会正常补取所需片段，不能与完整播放后的重播混为一谈。
- 验证暂停恢复、收起再打开、手机和电脑宽度、收礼页不预下载及直接起播、分享撤销后拒绝重新打开并释放旧媒体。保留 `no-store` 与接口授权检查。

## 实际边界

音频播放仍需要网络数据。浏览器可能按需补取未缓冲片段、回收内存缓冲；刷新、重开网页或切换身份后，也可能重新请求数据。**本轮保证应用不再强制“重新下载完整首歌后才让播放”，不承诺跨刷新离线缓存或所有浏览器永远零请求。** 网络持续慢于音频播放消耗时，仍可能出现短暂缓冲。

本轮没有在用户截图中的微信内置浏览器、真实 iOS 或 Android 设备上远程验收，也没有执行部署或停止用户开发服务。完成后只读核对线上首页及 4 个公开资源：`index-a748IdYq.js`、`AudioPreparation-B-Ok5q60.js`、`WorkDetailPage-CFBVUtnV.js`、`PublicGiftPage-BKpcvhbL.js`，均返回 200 且与已验证的本地构建逐字节一致。线上资源当前已包含修复，手机旧标签需要关闭并重新打开以加载新版。没有为本次核对读取用户私人音频。
