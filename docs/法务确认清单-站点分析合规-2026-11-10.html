一、当前事实（请法务先确认这四条属实）

  1. 隐私政策 privacy.html 已存在。§7.1 原文写明：分析数据保留期 “has not yet been determined and will be set by our legal review”，并声明 “We do not state a retention period in this Policy that has not been confirmed”。
  2. §10 Data Retention 仅表述“只保留合理必要时长”，并写明“上线前才会制定并公布分类保留表”，未给出具体天数。
  3. 政策载明 Effective Date: 13 November 2026，截至 2026-11-10 尚未生效； 《生产上线核验报告》§5 是“材料整理，供人工确认”的提问清单，不是法务回函；全仓无法务签字或审核通过记录。
  4. 相关代码能力已实现，但开关全关：retention.enabled=false、 retention-days=0、erasure.enabled=false、 erasure.method=""、调度未注册。
⚠ 未签字前：不得开启任何清理／擦除开关，不得对外发布含确定保留期的政策正文，不得宣告 PRODUCTION READY。

二、请逐项勾选（L1–L9）

L1分析数据的具体保留天数

技术侧建议（非法律结论）：13 个月（可覆盖同比统计）；《生产上线核验报告》§5.5 原举例为“13 / 24 个月”。最终以法务结论为准。
为何需签字：期限直接决定合法留存边界；填错会导致超期留存或过早删除。适用法（UK GDPR / EU GDPR / PIPL / 美国州法）及“最短必要期限”由法务判定，技术侧不下结论。
落地：qingfeng.analytics.retention.retention-days（当前 0，缺失或 ≤0 时清理任务拒绝执行）；privacy.html §7.1 Retention 句。

L2分析采集的法律基础：同意 vs 正当利益

技术侧建议（非法律结论）：当前横幅与代码是“明示同意、默认不采集、DNT 优先、可撤回”。若改选正当利益，横幅文案与撤回机制需重做。
为何需签字：决定激活前是否必须取得有效同意、撤回的法律效力，以及横幅措辞是否需法务背书。
落地：同意横幅文案、privacy.html §7.1 与法律基础章节。

L3撤回同意后，历史数据的处理方式

技术侧建议（非法律结论）：在 DELETE 与 ANONYMIZE 中择一；若选 AGGREGATE，请一并确认排期——代码现明确返回 UNSUPPORTED，绝不静默降级为删除。
为何需签字：三种方式的法律后果不同；技术侧不得替法务选，也不得声称任一种“必然”满足法律要求。
落地：qingfeng.analytics.erasure.method。

L4擦除范围：跨 visitor_id 与登录前匿名行

已核实事实：同一自然人可能有多个 visitor_id（多设备／清缓存）；登录前的匿名行无法可靠关联到账号，当前端点不强行关联。
为何需签字：“被遗忘权／删除权”是否要求覆盖全部历史，属法律判断；若要求覆盖，现有端点范围不足。
落地：擦除端点范围、是否新增身份关联方案。

L5历史数据的删除请求渠道

技术侧建议（非法律结论）：端点仅接受服务端会话身份，不接受任何客户端身份参数；启用前需确认身份验证方式与响应时限。
为何需签字：渠道决定权利行使是否可达、是否需对外公示，以及是否开放自助入口。
落地：qingfeng.analytics.erasure.enabled、privacy.html §7.1、前台入口。

L6隐私政策语种

已核实事实：现正文为英文，标题为“Privacy Policy隐私政策”；生效日 2026-11-13。
为何需签字：发布语种属合规与用户告知要求，技术侧不擅自增补译文。
落地：privacy.html 全文。

L7政策正文准确性复核（发布门槛）

已核实事实：§7.1 字段已与 track.ts / SiteEventController 逐项对齐；但保留期、删除方式、撤回路径仍为占位描述。
为何需签字：政策对外具有法律效力；措辞须经法务审核后方可发布，技术侧只保证“链接可达 + 字段描述与代码一致”。
落地：privacy.html §7.1、Effective Date。

L8哨兵值匿名化是否被认可为充分去标识

已核实事实：visitor_id / session_id 为 NOT NULL，匿名化只能置为常量 'ANONYMIZED'；creator_id / payload 置 NULL，聚合友好字段保留。
为何需签字：该结论直接决定 L3 可选哪种方式；技术侧不宣称哨兵值在法律上构成充分匿名化。
落地：erasure.method 是否允许 ANONYMIZE。

L9匿名用户人工申请流程是否满足删除权行使要求

已核实事实：匿名 visitor_id 仅存浏览器 localStorage，服务端无法据此验证申请人身份；当前只能走人工流程。
为何需签字：人工流程是否足以支撑权利行使、是否需额外验证或公示，属法律判断。
落地：privacy.html §7.1 相关表述、是否新增机制。

L10采集客户端 IP 并派生「国家」维度（V33 新增）

已核实事实：V33 迁移为 site_event 新增 country VARCHAR(64) 列及索引； 服务端从 X-Forwarded-For / X-Real-IP 解析真实客户端 IP，仅在 GeoIpResolver Bean 可用时， 经内嵌离线库 ip2region.xdb（JAR 内置，10.5 MB）离线解析出国家名后写入，原始 IP 字符串从不写入数据库或日志； 解析失败／私有地址／IPv6 一律置 NULL。该能力经 ObjectProvider<GeoIpResolver> 注入，Bean 缺失时自动降级为不采集。 privacy.html §7.1 已新增「Site Usage Analytics」小节披露此行为。
为何需签字：即便只保留派生国家名、不保留原始 IP，是否构成对 IP 的处理、是否需要单独同意／告知、是否落入地域统计的最小必要边界，属法律判断；技术侧不擅自判定。
落地：若否，需回退 V33 迁移与 SiteEventController 国家采集分支；若是，确认 privacy.html §7.1 披露措辞是否需补强。
