## 2. 三项问题的具体技术方案（建议，未实施）

### A. 数据保存期限 + 自动清理安全机制（可配置 + 分批清理 + 审计 + 多重安全护栏）

**设计原则**
- 保留期限**不得由开发人员硬编码**：经环境变量/服务端配置注入，具体值由法务确定（如 365 天），代码仅读配置。
- 支持按时间批量清理，避免一次性大删除导致锁表/复制延迟。
- 保留审计能力（每次清理运行记录）。
- 不影响看板正常统计（仅清理超出保留窗口的历史行）。

**安全护栏（本轮新增，强制）**
1. **独立启用开关，默认关闭**：新增 `qingfeng.analytics.retention.enabled=false`，与采集总开关 `qingfeng.analytics.enabled` 完全独立；未显式开启则清理任务**整体 no-op**。
2. **保留天数须法务确定，禁止擅自填生产默认值**：`qingfeng.analytics.retention-days` 若缺失或 ≤ 0，清理任务**拒绝执行（fail-closed）**，不在代码或配置中写入生产默认天数。
3. **单次删除数量上限**：每批 `LIMIT` 受 `batch-size` 控制（默认 1000，硬上限如 5000），防止单事务过大。
4. **执行前统计预计影响行数**：先 `SELECT COUNT(*)` 估算；若超过阈值（如 50000）**中止并告警**，需人工确认后再跑，防止配置错误导致大范围误删。
5. **分批独立事务**：每批 `DELETE … LIMIT ?` 在各自事务内提交，批间可限速；单批失败不影响已提交批次，不回滚整体。
6. **多实例互斥锁**：MySQL `GET_LOCK('site_event_cleanup', 0)` 在运行起始获取、结束释放；同时仅由指定节点（profile 标记）执行——双重防并发重复清理。
7. **时区与 cutoff 边界测试**：`created_at` 为 `TIMESTAMP`（UTC）。cutoff = UTC_NOW − `retention-days`。采用 `< cutoff` 语义并固化；测试 cutoff 边界两侧（恰好等于 cutoff 的行确定被包含/排除），覆盖夏令时/时区转换。
8. **失败重试、审计、告警**：异常时审计行标记 FAILED 并告警；有界退避重试，**绝不扩大删除范围**；重试仅针对未完成任务。
9. **生产启用前备份与副本演练**：正式开启前对生产库备份，并在数据库副本上演练清理，确认影响行数与性能可接受。
10. **防误删护栏**：DELETE 语句**必须含** `created_at < :cutoff` 谓词（缺此谓词直接抛错中止）；`retention-days` 过小（如 < 30）需显式 override 标志，否则拒绝。

**建议实现**
```sql
-- 每批（受索引 idx_site_event_created 支撑；每批独立事务）
DELETE FROM site_event WHERE created_at < ? ORDER BY created_at LIMIT ?;
```
- 调度：`@EnableScheduling` 配置类 + `@Scheduled(cron=低峰)` 调用；默认关闭由运维按开关开启；亦提供管理端手动触发 + **dry-run（仅统计不删）** 模式。
- 审计表 `site_event_cleanup_audit(run_id, cutoff_at, estimated_rows, rows_deleted, started_at, finished_at, status, lock_token)`。

#### A.2 清理任务互斥锁（可插拔接口，fail-closed）
- **独立锁接口**：定义 `CleanupLock` 接口（如 `Optional<LockHandle> tryAcquire()` + `LockHandle.release()`；`LockHandle` 实现 `AutoCloseable`），与具体数据库解耦；清理任务只依赖接口，不直接调用 `GET_LOCK`。
- **MySQL 实现**：`MysqlNamedCleanupLock` 使用命名锁 `SELECT GET_LOCK('site_event_cleanup', ?)`：返回 `1`=获取成功、`0`=被占用、`NULL`=错误；获取成功才返回 `LockHandle`，`release()` 调 `RELEASE_LOCK('site_event_cleanup')`。
- **H2 测试实现**：`InMemoryCleanupLock` 用 `ReentrantLock`/原子标志模拟，供单测注入"已占用""释放抛异常"等可控状态，**不依赖真实 MySQL**。
- **不支持可靠互斥锁的环境 fail-closed**：若 `CleanupLock` 实现标记为"不支持"或不可用，清理任务**整体拒绝执行**（abort + 告警），绝不降级为无锁运行。
- **锁获取失败不执行**：`tryAcquire()` 返回空（被占用/不支持）→ 清理任务直接跳过，**不删任何数据**。
- **必须释放锁（成功/失败/异常皆然）**：清理主体用 `try { … } finally { handle.close(); }`（或 try-with-resources）；即使清理过程抛异常，也先释放锁再向上传播；`release()` 自身抛异常时捕获并记录，不掩盖原始失败、不影响锁释放。

### B. 撤回同意后的历史数据处理（擦除授权重设计 + 三种处理方式）

#### B.1 三种处理方式区分
| 方式 | 操作 | 优点 | 局限 |
|------|------|------|------|
| **物理删除** | `DELETE` 整行 | 最强去标识/满足删除权 | 丢失该批原始数据的全部聚合价值 |
| **匿名化** | 保留行，剥离标识字段（见 B.3） | 保留页面/事件聚合趋势 | 见 B.4 残留再识别风险 |
| **聚合后保留** | 先汇总到日/小时汇总表，再删原始行 | 兼顾统计价值与去标识 | 需额外聚合管线，实施成本最高 |

> 具体采用哪种（或组合）**列为法务待确认 L3**，技术侧三种均给出可行实现。

#### B.2 登录用户擦除流程（服务端标识，拒绝客户端传入）
- **端点**（示例）：`DELETE /api/account/analytics-data`（登录态）。
- **标识来源唯一**：`creator_id` **仅**由服务端 `QF_SESSION`（`CreatorSessionFilter.token` → `identity.resolve`）取得，**绝不接受客户端传入的 creator_id**。
- **范围限制**：`WHERE creator_id = :sessionCreatorId`——仅当前登录用户自身数据；禁止任何 `OR`/全表路径。
- **幂等与重复请求**：删除/匿名化天然幂等（二次执行影响行数=0）；返回"已移除 N 行 / 剩余 0 行"；同一用户并发请求以审计去重。
- **审计与失败恢复**：每请求写 `erasure_audit(creator_id, method, rows_affected, requested_at, status)`；分批循环，单批独立事务，失败标记 FAILED 并允许重试，无部分损坏。
- **范围说明**：登录用户擦除覆盖其 `creator_id` 行；其登录前 `visitor_id` 匿名行无法可靠关联到账号（见 L4），可能残留——属法务待确认项，不在本端点强制覆盖。

#### B.3 匿名化可执行方案（遵守 NOT NULL 约束）
针对 1.1 约束，**不能用 NULL 替代 `visitor_id`/`session_id`**，采用常量哨兵值：
```sql
UPDATE site_event
SET visitor_id   = 'ANONYMIZED',
    session_id   = 'ANONYMIZED',
    creator_id   = NULL,          -- 可空，直接置空
    payload      = NULL           -- 可空，直接置空
WHERE creator_id = :sessionCreatorId;  -- 登录用户；匿名场景见 B.4
```
- 保留 `page_path`/`referrer`/`event`/`duration_ms`/`created_at`：均为已脱敏或聚合友好字段，用于保留页面/事件级趋势。
- 哨兵值 `'ANONYMIZED'` 跨多行复用，使原 `visitor_id` 关联断裂，无法再跨行追踪同一访客。

#### B.4 匿名化后是否仍可能识别（残留风险，须如实说明）
- 匿名化后 `visitor_id`/`session_id` 已去关联、`creator_id`/`payload` 已清空，**主要再识别路径被切断**。
- **但残留风险仍存在**：`page_path`（虽已脱敏，极端情况下特定路径组合）+ `referrer` + `event` 类型 + `duration_ms` + 高精度 `created_at`（TIMESTAMP(6)）的组合，理论上可形成行为指纹；若同一用户多条记录在匿名化前已被外部关联，匿名化无法撤销该关联。
- **不得声称**匿名化或删除"必然"满足法律要求；其仅为技术支撑措施，最终以法务结论（L3/L4）为准。

#### B.5 匿名用户擦除流程（不开放匿名删除 API）
- `visitor_id` 是 `localStorage` 中的随机 UUID，**不是身份认证凭证**，且无服务端绑定。
- **不允许**仅凭 localStorage 中的 `visitor_id` 开放 `DELETE /api/public/analytics-data?visitorId=…` 类公开 API：既无法验证请求者身份，也易被滥用。
- **若需支持匿名用户删除**：必须设计可靠身份验证、令牌签发、有效期、防重放与申请审核机制。当前**无法可靠验证匿名用户身份**。
- **明确建议**：匿名用户删除采用**人工申请流程**——用户通过隐私政策中的联系邮箱（如 `LabelManager@cheerfulmusic.co.uk`）提交请求，由**授权内部人员**在验证请求者后，使用受控的内部工具（非公开 API）按提供的 `visitor_id`/`creator_id` 执行删除/匿名化，全程审计。**本轮不开放匿名删除公开接口**。

#### B.6 匿名化统计污染防护（UV 口径排除哨兵值）
- **风险来源（已核实代码）**：`AnalyticsViewController.summary()` 的 totals 聚合（L151-158）与 daily 聚合（L159-163）以 `COUNT(DISTINCT visitor_id) uv`、`COUNT(DISTINCT session_id) sessions` 统计，筛选条件**仅** `WHERE created_at >= ?`。匿名化后 `visitor_id`/`session_id` 被置为常量哨兵值 `'ANONYMIZED'`；`COUNT(DISTINCT)` 会把全部匿名化行误算为 **1 个额外真实访客 / 1 个额外会话**，污染 UV 与 sessions 口径。
- **排除哨兵值（不改变正常访客口径）**：在上述聚合 SQL 的 `WHERE` 增加 `AND visitor_id <> 'ANONYMIZED'`（及 `AND session_id <> 'ANONYMIZED'`）。正常数据（无该哨兵值）行集合完全不变，**不引入任何口径偏差**；仅把匿名化行从 UV/sessions 聚合中剔除。
- **受影响面核查（已逐查询核对）**：
  - `summary()` totals（L151-158）与 daily（L159-163）：UV、sessions 受污染 → **必须加排除谓词**。
  - `pages`（L175-189，按 `page_path` 统计 pv/avg_duration）：匿名化行仍计入 `pv` → **建议同加排除**，避免匿名化后 pv 虚高。
  - `users`（L191+，用户排行，过滤 `WHERE s.creator_id IS NOT NULL AND s.creator_id <> ''`）：匿名化行 `creator_id = NULL` 被自动排除，**不受影响**，无需改动。
- **统一口径**：抽取共享谓词常量 `REAL_VISITOR_PREDICATE = "visitor_id <> 'ANONYMIZED' AND session_id <> 'ANONYMIZED'"`，`summary()`、`pages` 等聚合统一引用，避免散落硬编码导致后续遗漏。
- **测试要求**：新增"匿名化前后 UV 统计口径"测试（见 §6 B 匿名化统计口径、§15 验收条件 1）。

### 15.1 验收条件 1 — 匿名化统计污染防护（UV 口径排除哨兵值）

**风险及解决方案**
- **风险**：`AnalyticsViewController.summary()` 的 totals（L151-158）、daily（L159-163）聚合以 `COUNT(DISTINCT visitor_id) uv`、`COUNT(DISTINCT session_id) sessions` 统计，筛选仅 `WHERE created_at >= ?`。匿名化后 `visitor_id`/`session_id` 置为哨兵值 `'ANONYMIZED'`，`COUNT(DISTINCT)` 会把全部匿名化行误算为 1 个额外真实访客 / 1 个会话，污染 UV 与 sessions 口径；`pages`（L175-189）的 pv 也会含匿名化行而虚高。
- **解决方案**：聚合 SQL 的 `WHERE` 增加 `AND visitor_id <> 'ANONYMIZED' AND session_id <> 'ANONYMIZED'`；抽取共享谓词常量 `REAL_VISITOR_PREDICATE` 供 `summary()`、`pages` 统一引用。正常数据（无该哨兵值）行集合完全不变，**不引入任何口径偏差**；`users`（L191+，过滤 `creator_id IS NOT NULL`）自动排除，不受影响。

**开发验收标准**
1. 在含真实 `visitor_id` 行与若干 `'ANONYMIZED'` 行的混合数据集上，`summary()` 返回的 `uv` 等于真实访客数，`sessions` 等于真实会话数；**`'ANONYMIZED'` 多行只贡献 0 个真实访客，绝不误算为 1**。
2. `pages` 聚合的 `pv` 已排除匿名化行（或不计入哨兵值行）。
3. **正常数据口径回归**：纯真实数据下 UV/sessions/pv 与未加排除谓词时数值完全一致（提供对照断言）。
4. 共享谓词 `REAL_VISITOR_PREDICATE` 被 `summary()` 与 `pages` 聚合引用，未出现散落硬编码。

**自动化测试要求**

### 15.2 验收条件 2 — 清理任务互斥锁兼容性（可插拔接口，fail-closed）

**风险及解决方案**
- **风险**：原护栏仅依赖 MySQL `GET_LOCK('site_event_cleanup', 0)`，但在 H2 测试环境无等效函数、在"不支持可靠互斥锁"的部署形态下缺乏兜底，且缺失"获取失败/异常时必须释放锁"的规范，存在并发重复清理或无锁降级运行风险。
- **解决方案**：定义独立 `CleanupLock` 接口（`Optional<LockHandle> tryAcquire()` + `LockHandle.release()`；`LockHandle` 实现 `AutoCloseable`）。MySQL 实现 `MysqlNamedCleanupLock` 用命名锁；H2 用 `InMemoryCleanupLock`（ReentrantLock/原子标志）供单测注入可控状态；不支持可靠互斥锁的环境**整体 fail-closed** 拒绝执行；获取失败不执行；`try { … } finally { handle.close(); }`（或 try-with-resources）确保成功/失败/异常皆释放。

**开发验收标准**
1. **并发互斥**：两并发清理仅一实例获取 `LockHandle`，另一 `tryAcquire()` 返回空并跳过，不重复删数据。
2. **锁获取失败不执行**：注入"已占用/不支持"状态 → 清理任务 0 行删除并触发告警。
3. **异常必释放**：清理体抛异常路径中 `finally`/`try-with-resources` 先 `release()` 再向上传播；`release()` 自身抛异常被捕获、记录，不掩盖原始失败。
4. **H2 替代实现可用**：`InMemoryCleanupLock` 不依赖真实 MySQL 即通过全部锁用例。
5. **fail-closed**：锁实现标记"不支持" → 清理任务整体拒绝执行，绝不降级为无锁运行。
6. 清理任务只依赖 `CleanupLock` 接口，不直接调用 `GET_LOCK`。

**自动化测试要求**
- 见 §6 "A.2 互斥锁兼容性"：单测（`InMemoryCleanupLock` 注入"已占用"/"释放抛异常"等状态）覆盖并发互斥、获取失败不执行、异常释放、H2 替代、fail-closed；MySQL 命名锁集成测试覆盖 `GET_LOCK`/`RELEASE_LOCK` 返回码（1/0/NULL）语义。

**实施前置条件**
- §2.A 自动清理主体（含现有 10 项护栏）已落地，且仅通过 `CleanupLock` 接口获取/释放锁。
- 开发环境可用，H2（`MODE=MySQL`）+ MySQL 命名锁集成测试均可在 `@SpringBootTest` 下运行。
- 不依赖任何法务确认项（属纯工程兼容性修复）。
