按 Flyway `ChecksumCalculator` 语义复算：对文件逐行（`\r\n`/`\r`/`\n` 均视为分隔符）、按 UTF-8 字节做 CRC32、**不含行尾**、结果取有符号 32 位。

### 3.3 V27 / V28 究竟做了什么（只读反推自生产库结构）

- **V27 work soft delete** → `ALTER TABLE music_work ADD COLUMN deleted_at timestamp(6) NULL`（表名是 `music_work`，不是 `work`）
- **V28 quick creation** → 新建表 `quick_creation`（`id`/`work_id`/`work_version`/`request_key`/`language`/`status`/`lyrics_key`/`music_key`/`revision_id`/`task_id`/`error_code`/`lease_token` 等）
- 两者于 **2026-11-10 11:19** 直接在生产库执行，**绕过了应用内 Flyway**；JAR 只含 V1–V26
- 生产启动日志实证：
  ```

  WARN Schema `qingfeng_music` has a version (28) that is newer than the latest available migration (26) !
  Schema `qingfeng_music` is up to date. No migration necessary.
  ```
  即：当前"库里比 JAR 新"仅是 **WARN**（Flyway 对"未解析的已应用迁移"容忍）。

| 项 | 值 |

### 3.5 迁移编号分配方案

| 编号 | 归属 | 状态 | 处理要求 |
|---|---|---|---|
| V1–V26 | 历史 | 已在生产执行 | **禁止修改**（含内容与行尾） |
| **V27** | work soft delete | 已在生产执行，源文件缺失 | **禁止再用**；需补录基线文件（见 6.3），补录件**不得**参与 Flyway 执行 |
| **V28** | quick creation | 已在生产执行，源文件缺失 | 同上 |
| **V29** | **credit consumption（积分消耗）** | 空闲 | 从 V27 改号到 **V29** 后方可发布 |
| V30+ | 后续 | 空闲 | 顺序分配，禁止跳号 |

**强制规则**

1. 生产库 `flyway_schema_history` 是**唯一生产事实来源**；编号分配以"库中最大版本 + 1"为准，而非以 Git 中最大文件名为准。
2. **禁止修改已执行过的迁移文件**（内容、注释、行尾均不可动）——历史 V24/V25 的行尾漂移已是活教材。
3. **禁止删除或改写 `flyway_schema_history`** 解决冲突（含 `DELETE`/`UPDATE`/改 checksum）。
4. 冲突解法只有一个：**把新迁移改到未占用编号**。
5. 新迁移编号必须在**合并前**用生产库事实核验，并在 PR 中附"占用检查"结论。
6. 新增 `.gitattributes` 规则 `*.sql text eol=lf`（含 `*.md`、`*.java`、`*.ts` 等文本类型），保证同一提交在任何机器上产出**相同字节**，从根上消除 checksum 漂移。
