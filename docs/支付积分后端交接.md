# 支付与积分后端交接

## 当前状态

这是英国商户的支付与积分**沙箱开发框架**。Airwallex 目前固定使用沙箱，支付和积分扣费默认关闭，没有正式收款能力，也没有真实服务商沙箱交易验收。两者为独立开关，开启支付不会自动开启积分扣费。线上部署记录不能视为本次更改已上线。业务方案和定价讨论见[国际支付与积分方案](国际支付与积分方案.md)。

后端是 Java 17、Spring Boot、MySQL，使用 Flyway 管理数据库；前端为 Vue。支付创建订单前要求绑定 Google 账号。当前套餐由服务端配置，已加入用户确认的英镑及美元各三档，但尚未开放销售。无数据库的 local profile 不加载支付与积分持久化接口。PayPal 的新进度及配置见[PayPal 收款接入](PayPal收款接入.md)。

## 服务边界与数据

- 积分服务接口：`qf-business/.../credits/CreditsLedger.java`；JDBC 实现：`qf-infrastructure/.../persistence/credits/JdbcCreditsLedger.java`。记账使用整数积分，入账、扣减、退款分别以业务引用幂等；数据库事务与订单或任务状态提交一致。
- 支付订单及回调位于 `qf-server/.../server/payment/`：`PaymentController` 处理 HTTP 路由，`PaymentService` 处理订单、核对及入账事务，`PaymentGateway` 是渠道接口，`AirwallexSandboxGateway` 实现沙箱 HTTP、报文与回调验签。账户 API 只返回本人订单，Google 关联是购买前置条件。渠道凭证和金额只能由服务端使用或决定。
- 生成扣费在 `JdbcUsageBudget` 中按配置预扣；取消排队、供应商明确拒绝或明确失败时退回。供应商状态未知时保留记录，不能仅凭超时再次生成或自动退回。
- 数据迁移：`V15__credits_ledger.sql` 建立积分流水及锁；`V16__payment_orders.sql` 建立订单。现有账本使用全局行锁串行所有用户；可评估账户级锁和余额投影，但必须保持与流水的事务一致性，并在真实 MySQL 验证并发；不要绕过账本直接改余额。
- 订单现有状态为 `CREATING`、`PENDING`、`PAID`。服务端锁定账户并阻止同一账户并发创建未完成订单；订单列表仅返回最近 50 条。创建调用结果未知时保持待核对，现阶段没有安全取消或过期功能。

## 现有 HTTP 接口

除 webhook 外均要求已有 creator 会话；修改请求遵循现有 CSRF 机制。接口使用的价格为货币主单位，服务端决定套餐、金额、币种和积分数量。

| 接口 | 用途 |
| --- | --- |
| `GET /api/app/credits` | 返回 `balance`、`enabled`、`musicCost`。 |
| `GET /api/app/payments/catalog` | 返回 `enabled` 和 `packages`；未配置或未开启时无可购买套餐。 |
| `POST /api/app/payments/orders` | 提交 `packageId`；成功返回 `orderId`、`checkoutUrl`。绑定 Google，且不存在待处理订单才可创建。 |
| `GET /api/app/payments/orders` | 查询本人最近 50 笔订单，包括状态、积分和创建时间。 |
| `GET /api/app/payments/orders/{id}` | 只查询本人订单；有渠道链接时可主动向渠道核对，再返回状态。 |
| `POST /api/public/payments/airwallex/webhook` | 不依赖用户会话；验签、验账户并向渠道回查后才处理支付成功。 |

支付成功以服务端核验为准，浏览器跳转或查询参数不能作为发放积分的依据。回调处理要维持重复投递安全；订单金额、币种、引用、链接和成功支付状态不匹配时不得发放积分。渠道接口及事件规则应以[Airwallex 支付链接文档](https://www.airwallex.com/docs/api/payments/payment_links)和[回调验签文档](https://www.airwallex.com/docs/developer-tools/webhooks/listen-for-webhook-events)为准。

## 建议并行分工

1. **支付渠道与联调**：准备英国商户沙箱账号和服务端私有配置，验证银行卡、PayPal、微信各自的开通条件和实际支付流程；覆盖成功、失败、重复及延迟通知、签名与金额错误。把沙箱结果和实际渠道限制记录下来。
2. **订单生命周期与恢复**：设计服务端客户端幂等键、链接创建响应丢失后的查找和恢复、未付款订单安全取消/过期、定期对账与异常队列。验证跨设备、断网、重复请求、并发和服务重启，不得让状态未知直接变成失败或允许重复付款。
3. **退款、拒付及积分规则**：明确退款和拒付如何关联原订单与积分流水、积分已使用时如何处理、人工介入与审计；实现并验证重复和乱序事件。单独确认赠送、有效期、定价及税务，不把示例价格当生产配置。
4. **运维与上线验证**：建立独立测试数据库，检查 V15/V16 在真实 MySQL 的迁移、回滚和备份；设置私有凭证、回调 HTTPS、监控和告警。制定从沙箱切换生产的方案并完成端到端验证。

以上工作包可并行；涉及订单状态、账本事件或 API 变更时先协调接口和迁移版本，避免同一张表的改动冲突。任何一项未完成都不应开放真实收款。

## 本地验证

在 `Qingfeng_AI_Music` 执行 `mvn test`；在 `Qingfeng_AI_Music_VUE` 执行 `npm test` 和 `npm run build`。后端现有测试在测试环境中构造支付结果和回调，不代表完整渠道 HTTP 往返，也不代替真实 MySQL 与 Airwallex 沙箱的端到端验收。

沙箱配置项和回调路径见[国际支付与积分方案](国际支付与积分方案.md)。密钥放在服务端私有配置或安全的环境变量中，不要提交到 Git、放入前端或写到交接文档；不应在聊天中传递凭证。
