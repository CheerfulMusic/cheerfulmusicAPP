# AI 改写歌词成本与积分定价审计报告

- 审计日期：2026-11-10
- 审计范围：`/api/app/inspiration/rewrite`（AI 改写歌词）及其同源 AI 调用
- 审计性质：**只读审计**。未修改任何 Java / Vue / 数据库 / 配置，未调用真实 AI API，未连接生产库，未执行 Git 写操作
- 结论摘要：**AI 改写歌词当前零计费、零流水、零审计**。真实单次成本极低（典型场景 ≈ $0.0003），但**当前缺乏调用量可观测性与成本上限**，且同链路的「Agent 参考分析」是**全自动触发**，风险高于手动触发的改写

## 一、AI 改写完整调用链

### 1.2 后端链路

```
POST /api/app/inspiration/rewrite
  → InspirationController.rewrite()            qf-server/.../web/app/InspirationController.java:12,18-21
      @Valid RewriteRequest{text ≤4000, language ∈ {zh-CN,en,mixed}}

      · slots(Semaphore)   → 全局并发 N，超出抛 REWRITE_GENERATION_BUSY
  → DeepSeekInspirationRewriter.rewrite()     qf-infrastructure/.../provider/DeepSeekInspirationRewriter.java:42-67
      → HttpClient.send() → https://api.deepseek.com/chat/completions
      → 返回 JSON {"text": "..."}，text 长度 ≤ maxLength(4000)
```

### 1.3 关键事实

- **端点硬编码**：`DeepSeekInspirationRewriter.java:35` → `https://api.deepseek.com/chat/completions`，**没有 endpoint 配置项**，部署侧无法改指向上游网关
- **无重试**：只有一次 `client.send()`（`:50`），失败即抛错，无退避重试
- **不落库**：`InspirationRewriteService` 无任何 repository 依赖；改写调用**不写** `credit_ledger`、**不写** `credit_consumption`、**不写** `model_usage_reservation`
- **不扣额度**：全链路无 `UsageBudget.reserve` / `CreditsLedger` 调用（`grep CreditsLedger|UsageBudget|credits\.` 在 `InspirationRewriteService.java`、`InspirationRewriter.java`、`DeepSeekInspirationRewriter.java`、`InspirationController.java` 中**零命中**）
- **不存在自动/重复触发**：两个前端入口都要求用户显式点击；无 debounce 触发的模型调用、无轮询、无重试风暴

| # | 风险 | 等级 | 说明 |

## 七、三种积分定价方案对比

> 价格由产品决策确定，本报告**不擅自定价**，只给出定价区间依据。

### 7.1 方案 A：完全免费（保持现状 + 强化限流）

**做法**：维持零收费，新增**每日改写次数上限**（建议按 `qingfeng.usage` 现有配额风格配置，例如 `qingfeng.usage.rewrite.daily-per-creator`），并把 `agent/reference` 的自动调用纳入同一配额。

| 维度 | 评价 |
|---|---|
| 用户体验 | ⭐⭐⭐⭐⭐ 零门槛，新用户体验最顺，改写是「创作前辅助」而非「作品产出」 |
| 平台成本 | ⭐⭐ 需靠每日配额封顶；无配额时单用户最高 $25–340/天 |
| 商业化能力 | ⭐⭐ 改写不产生收入，只增加最终生成歌词/歌曲的转化率 |
| 实施复杂度 | ⭐⭐⭐⭐ 低。**需新增每日配额计数**（跨实例落库），约等于现有 `model_usage_reservation` 的日维度扩展 |
| 滥用风险 | 🟠 中。配额封顶后可控；但 `agent/reference` 自动触发需要额外兜底 |

### 7.2 方案 B：每日免费额度 + 超额积分收费

**做法**：每日赠送 N 次免费改写（可用现有「首登赠送积分」式的账本发放，或新增每日配额表）；超出后每次扣 X 积分。免费额度内**不扣积分但记流水**，便于成本核算。

| 维度 | 评价 |
|---|---|
| 用户体验 | ⭐⭐⭐⭐ 日常使用无感付费，新用户可完整试用；重度用户才感知成本 |
| 平台成本 | ⭐⭐⭐⭐ 免费额度封顶 + 超额收费，成本有上界 |
| 商业化能力 | ⭐⭐⭐⭐ 保留转化漏斗，同时对高频用户产生收入 |
| 实施复杂度 | ⭐⭐ **高**。需：① 新增每日额度表（新迁移）；② 免费额度与积分双轨判定；③ 流水区分「免费/付费」；④ 前端展示剩余免费次数 |
| 滥用风险 | 🭐⭐⭐ 低。免费额度 + 付费超额双重封顶 |

### 7.3 方案 C：每次调用固定积分（与现有体系一致）

**做法**：每次改写扣固定 X 积分，复用 `CreditsPricing` + `CreditsLedger` + `CreditConsumptions`，失败不扣费（与歌词生成同构）。

| 维度 | 评价 |
|---|---|
| 用户体验 | ⭐⭐ 每次点击都消耗资源，重复试错成本高；需明确「本次改写消耗 X 积分」提示 |
| 平台成本 | ⭐⭐⭐⭐⭐ 成本完全回收且有上界 |
| 商业化能力 | ⭐⭐⭐⭐⭐ 与歌词/歌曲统一，积分体系完整 |
| 实施复杂度 | ⭐⭐⭐ 中。需：① `CreditsPricing.Kind` 新增档位；② 参考键形态调整（见 9.1）；③ 前端提示与拦截；④ 流水类型 |
| 滥用风险 | ⭐⭐⭐⭐⭐ 最低，积分天然限制调用量 |

### 7.4 对比总表

| 维度 | A 免费+配额 | B 免费额度+超额收费 | C 固定积分 |
|---|---|---|---|
| 用户体验 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ |

## 八、推荐方案与理由

**推荐：方案 B（每日免费额度 + 超额积分收费），并以方案 C 的扣费机制作为「超额部分」的实现载体。**

理由：

1. **成本真实量级决定不宜按次全收费**。典型调用 ≈ $0.0003、1 积分 ≈ $0.086–0.099，即 1 积分 ≈ 148–337 次典型调用。若每次直接扣 1 积分（方案 C 全量），相对真实成本溢价 25–337 倍，**在「辅助性输入优化」场景下性价比极差**，会直接压低新用户转化，而改写恰恰是提升后续歌词生成质量与付费意愿的关键漏斗。
2. **纯免费（方案 A）无法自证价值，也无法止血**。在补齐每日配额与调用审计之前，A 是在赌「没人滥用」——而按 6.2 的量化，单账号每天可造成 $25–340 的账单。
3. **B 同时解决三件事**：新用户体验不被门槛卡住（免费额度内零感知）、平台成本有硬上界（配额 + 付费）、高频/批量用户自然转为付费（产生收入）。
4. **B 的实现可复用已完成的歌词积分基建**：超额部分直接复用 `CreditsPricing` / `CreditsLedger.debit` / `CreditsLedger.refund` / `CreditConsumptions`（`V27` 迁移已就位），与歌词生成共用同一套「预扣 → 成功结算 → 失败退款 → 幂等」链路，**不需要第二套积分系统**。
5. **先补可观测性再定价**。无论选哪个方案，**第一件事都应是记录 `usage` 与调用次数**（见 9.3），否则定价缺少依据，事后也无法归因。

**建议的定价区间（供产品决策，非最终结论）**：

- 免费额度：每日 3–10 次改写（覆盖绝大多数真实使用 —— 一次创作通常润色 1–2 次）
- 超额单价：**1 积分/次**（与歌词生成 5 积分形成"辅助 vs 产出"的清晰层级）
- 成本校验：按 1 积分 = $0.0713–$0.0990，超额部分的收入/成本比约 25–337 倍，**不存在定价低于成本的风险**

## 十、当前代码是否具备接入统一积分系统的条件

**结论：具备约 80% 的基础设施，但存在 3 个必须先补的结构性缺口，不能直接照搬歌词生成的实现。**

### 10.1 已具备（可直接复用）

| 能力 | 位置 | 可复用性 |
|---|---|---|
| 统一积分账本（扣费/退款/幂等/并发保护） | `CreditsLedger` / `JdbcCreditsLedger` | ✅ 完全复用，参考键换形态即可 |
| 统一定价服务 | `CreditsPricing` / `EnvironmentCreditsPricing` | ✅ 加一个 `Kind` + 一个配置项 |
| 消费流水表 | `CreditConsumptions` / `JdbcCreditConsumptions` + **V27 迁移已就位** | ⚠️ 表结构需一处调整（见 10.2） |
| 「预扣 → 成功结算 → 失败退款 → 幂等」范式 | `JdbcCompositionRequests`（本轮歌词积分已落地并通过 15 项集成测试） | ✅ 可作为模板 |
| 积分余额统一出口 | `CreditsController` `app/credits` | ✅ 增加字段即可，前端零硬编码 |
| 前端提示与拦截基建 | `CreditCostHint.vue` / `credit-gate.ts` / `useCredits.ts` / `credit-balance.ts` | ✅ 加 variant 与文案即可 |

### 10.2 必须先补的 3 个缺口

| # | 缺口 | 影响 | 需要的改动 |
|---|---|---|---|
| **G1** | **改写没有 workId**：`model_usage_reservation.work_id` 与 `credit_consumption.work_id` 均 `NOT NULL` 且有外键 | 额度与流水表都无法直接承载改写 | 新增迁移把 `work_id` 改为可空（V28+），或为改写单独建表 |
| **G2** | **改写没有幂等键**：`RewriteRequest` 只有 `text` + `language`，前端也不传 requestKey | 重复提交无法幂等，扣费会重复；也无法做「失败不扣费」的精确对账 | 前后端都增加 `requestKey`（UUID，格式与歌词生成一致） |
| **G3** | **额度路径与 work 强绑定**：`UsageBudget.reserve(owner, work, key, kind)` 签名要求 work | 无法直接用 `JdbcUsageBudget` 给改写做额度预留 | 要么扩展 `reserve` 允许 work 为空（需调整外键与 `active()` 查询），要么为改写单独实现额度路径 |

### 10.3 附加说明

- `CreditsPricing.Kind` 当前只有 `MUSIC` / `LYRICS` 两档 —— **新增档位是设计上的既定扩展点**，不是重构 ✅
- `CreditConsumptions.consumption_type` 已是字符串列，新增类型无需改表结构 ✅
- **不需要第二套积分系统**：所有扣费都走 `CreditsLedger`，余额只有一个来源 ✅
