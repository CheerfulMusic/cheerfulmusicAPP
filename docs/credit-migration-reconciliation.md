# 积分迁移编号统一

以生产库已经登记的版本为准。保留 V27 作品软删除、V28 一键创作和 V29 歌词版本设置。原积分 V27、V28 分别改用 V30、V31。合并远端分支时，只保留这两个新的积分 SQL 文件，移除同一功能的旧编号文件。

生产库只读核对显示，V27～V29 已成功登记。积分消费、每日配额和改写消费三张表已经存在，Flyway 历史里没有对应的积分迁移。表存在与迁移已登记是两件事。

## 验证与上线

1. 在目标库检查 Flyway 历史和积分表的实际结构。可用下方只读入口核对字段、索引和关联键。表结构不匹配时先做差异分析，避免把结构不完整的表当作迁移成功。
2. 在隔离 MySQL 验证空库安装、已有三张表的升级和部分建表后的升级。V30/V31 使用随表声明的索引，已有的匹配表保留数据，缺失的表一次创建完整结构。
3. 主库应用继续关闭自动迁移。正式上线时按独立的备份与审批流程决定是否通过 Flyway 登记 V30/V31。手工 JDBC 建表入口不登记版本。MySQL DDL 隐式提交，执行中断后先检查结构。
4. 如果其他长期数据库曾把积分迁移登记在 V27/V28，先对照该库的结构和历史设计单独的迁移路径。不要直接运行统一编号的脚本或使用 repair 将两种历史视为同一套。

从项目根目录运行，只读检查省略 `--apply`。私有配置保存在仓库外或忽略提交的目录中。

```text
java -cp "<mysql-connector-j.jar>" scripts/apply-credit-migration.java <私有配置路径>
```
