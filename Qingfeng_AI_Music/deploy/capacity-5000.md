# 5000 并发容量配置

`capacity-5000` 是写入节点的附加 Spring profile。它允许最多 5000 个音乐生成任务占用准入名额。用户提交成功时，任务、积分快照和待处理事件已在数据库事务内提交。后台仍按供应商合同额度派发。新任务的每账号并发上限沿用 1。

## 启用和回滚

按项目上线流程固定发布提交、测试、构建、备份。首次启用时，停止所有音乐写入实例，在主库执行 JAR 资源 `db/optional/music_admission_permits.sql`。该脚本添加一张含 32 行的调度表，适用于当前 Core44 库。检查 `SELECT COUNT(*) FROM music_admission_permit` 返回 32。

在所有写入节点保留现有 profile 并追加 `capacity-5000`。检查外部配置的最终有效值为 `qingfeng.usage.music.permits-enabled=true`、`qingfeng.usage.music.concurrent-global=5000` 和 `qingfeng.usage.music.daily-global=-1`。部署时统一切换所有写入节点，混用不同的准入规则会使全站上限失去意义。启动失败时检查新增调度表和有效配置。

应用从数据库分批领取名额，每批最多 512 个，名额在 32 行间分配。任务写入回滚时，数据库同时退回本次名额。补充名额前会等待进行中的写入提交，重新统计已有任务。进程重启会丢弃剩余的预分配名额，按实际任务重新计算。供应商迟到的受理回执仍会保存，并使后续准入重新核对容量。

入口容量需单独核对。5000 个同时转发的请求最多需要约 5000 条客户端连接和 5000 条上游连接。用 `nginx -T` 核对实际 worker 数及 `worker_connections`，并用 `/proc/<pid>/limits` 核对 Nginx 和 Java 进程的文件描述符上限。四个 worker 可从每个 8192 个连接槽、每进程 16384 个文件描述符起测。通过预发布域名验证 TLS、代理和下载流量后，再确定线上容量。

回滚时统一停止写入节点，恢复原版本和原 profile，再按上线流程检查健康。保留调度表、任务和积分流水。回滚到较低上限后，已受理任务继续处理，活跃数降到上限以下后才接受新任务。观察已有指标 `qingfeng.generation.inflight` 和 `qingfeng.generation.oldest.ready.seconds` 跟踪供应商在途数和队首等待时间。

## 隔离验收

在独立的本机 MySQL 8 测试进程中创建一个空库，库名采用 `qf_capacity_http` 或 `qf_capacity_http_数字`，监听地址为 `127.0.0.1`，端口为 `57xxx`。测试沿用项目专用 MySQL 测试实例的 root 空密码约定。每次使用新的空库。测试使用离线音乐供应商和测试积分。

从 `Qingfeng_AI_Music` 目录运行以下命令。示例端口为 57832。

```powershell
mvn -pl qf-server -am test '-Dtest=MusicCapacityHttpTest' '-Dsurefire.failIfNoSpecifiedTests=false' '-Dqf.capacity=true' '-Dqf.capacity.mysqlPort=57832' '-Dqf.capacity.schema=qf_capacity_http_1'
```

默认验证 5000 个独立会话和 5000 条同时打开的 TCP 连接，轮询作品列表、作品详情和生成记录。持续读负载为 30 分钟、每秒 500 次请求，另加 10 秒每秒 1000 次请求。生成阶段在 10 秒内投放 5000 个不同的已确认作品，再重放同一批请求。响应时间从计划发出时刻计算，包含客户端等待；读请求 P95 上限为 500 毫秒，提交 P95 上限为 1 秒。验收还核对任务数、扣费数、满额拒绝和取消后的退款与名额复用。`-Dqf.capacity.seconds=15` 可缩短持续读阶段，用于开发迭代。单独在新的空库上增加 `-Dqf.capacity.fenced=true` 可验证 V53 积分批次记账。测试启动前会核对实际端口、绑定地址、库名和空库状态。


## 本次验收结果

2026-11-21，在同一台 Ryzen 7 5800H 测试机上运行压力客户端、Java 17 应用和 MySQL 8.0.46。HTTP 直连本机应用。测试会话分别拥有自己的作品、已确认歌词和积分。

| 场景 | 样本 | 结果 |
| --- | --- | --- |
| Core44 持续读取 | 5000 会话，500 请求/秒，30 分钟 | 900000 次成功，P95 19 ms，P99 30 ms |
| Core44 短时读取 | 1000 请求/秒，10 秒 | 10000 次成功，P95 18 ms |
| Core44 生成提交 | 5000 个作品，500 请求/秒 | 全部入队，P95 303 ms |
| V53 同时打开连接后集中读作品 | 5000 条 TCP 连接 | 5000 份作品响应均校验成功，2.48 秒收齐 |
| V53 启用积分批次记账的生成提交 | 5000 个作品，500 请求/秒 | 全部入队，P95 447 ms；同批重放 P95 27 ms |

两种账本都通过了任务数、扣费数、满队列拒绝和取消退款检查。音乐派发器在压力测试中关闭，供应商使用离线实现。线上公网、媒体传输、支付服务和真实出歌时长需要分别测量。

## 支付回调积压处理

在支付 worker 上设置 `qingfeng.payment.inbox.batch-size` 可控制每个线程单轮最多尝试处理的事件数。默认 10，范围 1～256，容量 profile 取 128。独立 worker 可以单独设置此项。仅启用支付收件箱调度的进程会使用它。回退为 10 并按正常发布流程重启即可。

2026-11-22 在独立 MySQL 8.0.46、V53 积分账本和离线 Stripe 网关下，固定 4 个线程、1 秒扫描间隔，依次运行两组、每组 2500 个不同用户的订单。通过 HTTP 创建订单并投递签名回调，每 100 笔重放一次。计时从积压准备完毕开始，至该组所有成功回调处理完成为止，包含同一收件箱中对账事件的竞争。批量 10 用时 139.10 秒，批量 128 用时 58.69 秒，分别约为每秒 18.0 和 42.6 笔。逐单核对了 PAID 状态、唯一积分入账流水和用户余额。这是后台积压消化速度，未测量真实渠道下单响应时间和外部支付成功率。

可在项目已有的全新隔离支付 MySQL 测试环境中运行 `IntegratedPaymentApplicationMySqlTest#drainVerifiedStripeBacklog`，并传入 `-Dqf.payment.capacity=true` 复测。开启该专项测试时，提高的回调接收限额仅用于隔离测试实例。
